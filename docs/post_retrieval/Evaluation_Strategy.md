# Evaluation Strategy: Generation Stage

This document defines the metrics and methodology used to evaluate the answers generated by the RAG pipeline.

## Metrics

We use a combination of automated metrics to assess different aspects of the generated answers.

### 1. Semantic Answer Similarity (SAS)
-   **Definition**: Measures the semantic similarity between the generated answer and the ground truth.
-   **Calculation**: Uses a SentenceTransformer model (`all-MiniLM-L6-v2`) to encode both answers into embeddings and calculates the cosine similarity.
-   **Scale**: 0.0 to 1.0 (Higher is better).
-   **Applied to**: Both RAG answer and Baseline answer (for direct comparison).

### 2. ROUGE-L
-   **Definition**: Measures the Longest Common Subsequence (LCS) of words between the generated answer and the ground truth. Captures literal lexical overlap.
-   **Scale**: 0.0 to 1.0 (Higher is better).
-   **Applied to**: Both RAG answer and Baseline answer.

### 3. LLM-as-a-Judge (Factual Accuracy)
-   **Definition**: TinyLlama-1.1B acts as an automated evaluator to determine if the generated answer is factually correct relative to the ground truth.
-   **Methodology**:
    -   **Few-Shot Prompting**: Two concrete solved examples are embedded in the prompt to enforce consistent `[[1]]`/`[[0]]` output formatting.
    -   **Chain-of-Thought (CoT)**: The judge is forced to generate a textual reasoning chain *before* outputting the binary score. This prevents rushed, inaccurate classifications.
    -   **Stop Marker (`###`)**: The prompt instructs the model to end its response with `###`. The script splits the response at this token before regex parsing, preventing example leakage.
    -   **Binary Classification**: Outputs `[[1]]` (Correct) or `[[0]]` (Incorrect), extracted via regex.
-   **Auditability**: The `judge_raw_response` field is saved per question, allowing manual verification of the judge's reasoning chain.
-   **Scale**: Binary (0 or 1), aggregated as Accuracy (mean over all questions).
-   **Achieved Accuracy**: 1.0 (100%) on the n=15 validation run after few-shot CoT hardening.

## Baseline Comparison (Mandatory)

Every evaluation run **always** generates two answers per question:
1. **RAG Answer**: Generated with retrieved + re-ranked context injected into the prompt.
2. **Baseline Answer**: Generated by the same model with **no context** (pure parametric knowledge).

All three metrics are computed for both answers. The difference (Δ RAG − Baseline) is the primary indicator of the retrieval augmentation's contribution.

The baseline generator uses `max_new_tokens=128` and is instructed to answer in 1-2 complete sentences without bullet points.

## Evaluation Workflow

1.  **Input**: Retrieval results JSON + questions dataset + canonical paper records.
2.  **Generation**:
    -   RAG answer generated using the top-3 re-ranked context chunks.
    -   Baseline answer generated with no context from the same model.
3.  **Scoring**:
    -   SAS and ROUGE-L calculated for both RAG and Baseline answers against `text_answer` ground truth.
    -   LLM Judge evaluates the RAG answer's factual correctness.
4.  **Logging**:
    -   All metrics and raw judge responses saved to the output path (default: `data/intermediate/post_retrieval/generation_evaluation.json`).

## Usage

```bash
# Standard run (n=15, default output path)
python -m src.post_retrieval.scripts.run_evaluate_generation --representation title_only --limit 15

# Scale run (n=50, separate output file to preserve previous results)
python -m src.post_retrieval.scripts.run_evaluate_generation --representation title_only --limit 50 --output-path data/intermediate/post_retrieval/generation_evaluation_n50.json

# Skip cross-encoder re-ranking (faster, ablation study)
python -m src.post_retrieval.scripts.run_evaluate_generation --representation title_only --skip-cross-encoder
```
